## 执行摘要

HAL（HotelAgent Link）是一个革命性的AI Agent底层交易协议，旨在用AI取代传统OTA中介，重构文旅行业生产关系。我们的核心使命是：用AI替代携程式中介，把价值还给用户与商家。

### 核心定位

我们不是在做一个新的旅游App，而是在为未来10年所有的AI助手建设一套连接文旅物理世界的底层清算协议。我们不生产流量，我们是流量变现的必经之路。

### 一句话价值主张

"用硅谷最顶层的逻辑（Agent生态），去解决大理最泥泞的问题（非标预订）。"

## 第一章：市场分析与机会识别

### 1.1 市场规模测算（三阶段演进）

#### 1.1.1 近期（1-2年）：存量市场的数字化替代

**市场规模**：约10亿人民币/年

**市场定义**：景区/民宿的AI数字化改造费 + 基础SaaS订阅费

**测算逻辑**：
- 以大理为例：约7000家民宿，20%的精品民宿（1400家）愿意每年支付5000元，单大理市场达700万
- 放眼全国（莫干山、三亚、丽江、延吉等），精品民宿及非标住宿约有20万家
- 20万家 × 5000元/年 = 10亿元/年

**商业本质**：这个阶段你赚的是"省钱"的钱。帮老板省掉夜班前台、省掉美工、省掉微信客服的人力成本。

#### 1.1.2 中期（3-5年）：存量交易额的费率重构

**市场规模**：约80-120亿人民币/年

**市场定义**：存量直连交易的技术服务费（Take Rate）

**测算逻辑**：
- 中国在线旅游市场（OTA）年交易额（GMV）约1.5-2万亿
- 其中约20%-30%的高端非标住宿极其渴望摆脱15%的佣金（约4000-6000亿GMV）
- 若HAL协议能切入其中10%的交易流（400-600亿GMV），按2%的技术服务费计算
- 市场规模：80-120亿人民币/年

**商业本质**：这个阶段你赚的是"分利"的钱。你从OTA嘴里抢肉，把15%的佣金拆解，自己拿2%，还给商家和用户13%。

#### 1.1.3 远期（5-10年）：AI Agent时代的"文旅路由器"

**市场规模**：中国区潜力500-1000亿人民币/年

**市场定义**：全网AI流量的文旅分发税 + 跨行业数据资产溢价

**愿景描述**：
- 当C端彻底习惯"AI一键订房"，所有大模型（OpenAI、豆包、Kimi）都需要通过HAL这种"协议层"来连接物理世界
- 不仅处理订房，还处理租车、向导、餐饮、在地体验等全产业链
- 成为文旅界的Visa/银联，AI发起文旅交易的必经之路

**商业本质**：这个阶段你赚的是"税收"的钱。只要AI发起文旅交易，就要走你的协议，你坐收万分之几或百分之几的流量过路费。

| 形态 | 代表玩家 | 现状描述 | 局限性 |
|------|---------|---------|--------|

#### 1.4.2 国际现状：协议驱动与"Agent First"的尝试

**发展阶段**：由于API文化普及，更接近"生态"状态，但在非标垂直领域仍做得不够深

| 形态 | 代表玩家 | 现状描述 | 局限性 |

| 去中心化协议 | Dtravel、 Winding Tree | 尝试Web3协议的去中心化预订 | 缺乏AI"大脑"，用户需理解复杂协议，门槛高 |
| OS级智能体 | OpenAI、Apple、Google | 试图让手机系统变成Agent，直接接管订房 | 通用大脑，不理解垂直领域，需要垂直"数据节点"供血 |

#### 1.4.3 HAL的差异化定位：垂直领域的"第三条道路"

| 维度 | OTA模式 | 独立SaaS模式 | HAL模式 |
|-----|---------|-------------|---------|
| 形态 | 平台（抽成15%） | 软件工具 | 协议层基建 |
| 关系 | 商家→平台→用户 | 商家→软件→用户 | 商家Agent ↔ 协议 ↔ 用户Agent |
| 佣金 | 15% | 无佣金但无流量 | 技术过路费（2-3%） |
| 流量来源 | 平台购买 | 无流量 | AI大模型原生流量 |
| 数据归属 | 平台 | 软件商 | 商家自有 |

## 第二章：产品与服务体系

### 2.1 核心产品架构

#### 2.1.1 HAL协议定位

HAL（HotelAgent Link）不是一个App，而是一层"翻译协议"。它的核心功能是：

```
酒店PMS数据 → HAL中间件 → AI翻译官/数字分身 → 终端用户
                      ↑
              无缝对接全球AI助手
```

#### 2.1.2 技术架构设计（三层架构）

| 层级 | 技术选型 | 核心功能 |
|------|---------|---------|
| **交互层** | 多模态LLM + 语音/文字混合交互 | 理解用户自然语言需求 |
| **代理层** | Agent框架（ReAct+Tool-use） | 调用外部API，完成预订闭环 |
| **数据层** | 实时库存（酒店PMS/航司GDS）+ 知识图谱 | POI、交通、天气、签证政策等 |

#### 2.1.3 SaaS插件形态

SaaS插件以"中间件盒子"（Middleware Box）形式存在，核心作用是将酒店内部数据翻译成大模型能理解的语言。

**技术栈构成**：
- 后端开发：Python (FastAPI) / Go（处理高并发和AI接口对接）
- 结构化数据库：MySQL / PostgreSQL（存储房态、价格、订单）
- 向量数据库：Milvus / Pinecone（存储酒店软性描述，语义理解关键）

### 2.2 核心功能模块

#### 2.2.1 PMS连接器

**功能描述**：对接酒店现有管理系统（如绿云、西软），读取房态数据

**实现方案**：
- 有PMS的酒店：写接口读取房态、价格、订单
- 无PMS的小微民宿：提供极简微信小程序端，让老板手动管理房态

**技术挑战**：这是最难的脏活，需要处理不同厂商的接口差异

#### 2.2.2 Prompt引擎

**功能描述**：把读取到的数据，包装成给AI看的提示词

**核心能力**：将非标特色转化为AI的语言，让AI理解"安静"、"适合发呆"、"服务员人情味"等软性描述

#### 2.2.3 Function Calling接口

**功能描述**：定义标准JSON格式，使大模型可调用查询房态、下单等接口

**实现方式**：
1. 在SaaS中定义API（如 `get_hotel_price(date, room_type)`）
2. 在大模型开发者后台填写API地址并编写功能描述
3. 当用户提问时，大模型自动调用API获取数据并回复用户

### 2.3 多模型适配策略

针对中国大陆市场，采用"通用适配器"模式，对接三大阵营：

| 阵营 | 代表产品 | 对接方式 |
|------|---------|---------|
| 百度 | 文心一言/灵境矩阵 | 在百度Agent开发平台注册为插件 |
| 阿里 | 通义千问 | 通过阿里生态（钉钉、淘宝、夸克）接入 |
| 字节 | 豆包/Coze | 利用Coze平台搭建Agent |

### 2.4 核心产品优势

| 优势类别 | 具体描述 |
|----------|---------|
| **去中介化** | 摆脱OTA 15%佣金模式，仅收取技术服务费（可低至2元/单） |
| **数据主权** | 服务器部署国内，保障数据合规与安全 |
| **语义理解** | 向量数据库存储软性描述，实现"安静"、人情味等非结构化搜索 |
| **多端接入** | 酒店方通过网页后台或微信小程序勾选接入权限 |
| **低门槛** | 酒店老板无需懂技术，只需配置权限；用户扫码即可通过AI对话完成预订 |
| **可扩展性** | 验证单店MVP后，可快速复制去中心化部署模式 |

## 第四章：技术实现方案

### 4.1 技术架构总览

```
┌─────────────────────────────────────────────────────────────────┐
│                        交互层                                    │
│           多模态LLM + 语音/文字混合交互                          │
│                  （理解用户自然语言需求）                         │
├─────────────────────────────────────────────────────────────────┤
│                        代理层                                    │
│          Agent框架（ReAct+Tool-use）                            │
│              （调用外部API，完成预订闭环）                       │
├─────────────────────────────────────────────────────────────────┤
│                        数据层                                    │
│    实时库存        │        知识图谱                            │
│  酒店PMS/航司GDS  │   POI/交通/天气/签证政策                   │
│      +            │        +                                   │
│    向量数据库      │        结构化数据库                        │
│   （语义搜索）     │    （房态/价格/订单）                      │
└─────────────────────────────────────────────────────────────────┘
```

### 4.2 核心功能模块详解

#### 4.2.1 PMS直连技术路径

| 阶段 | 任务 | 时间 | 关键挑战 |
|------|------|------|---------|
| 1 | 厂商调研：梳理石基/绿云/西软等TOP10接口文档 | 2周 | 字段差异大 |
| 2 | NDA谈判：签署保密协议，获取API文档 | 2周 | 厂商配合度 |
| 3 | 适配器开发：统一封装查询/下单/取消接口 | 4周 | 接口标准化 |
| 4 | 沙箱测试：模拟高并发库存查询，制定限流策略 | 2周 | 性能稳定性 |
| 5 | 灰度上线：先接入100家试点酒店，持续异常订单回滚 | 持续 | 用户体验 |

**关键成功因素**：建立标准化API适配框架，降低后续接入成本。

#### 4.2.2 大模型对接机制

**Function Calling流程**：
1. 在SaaS中定义API（如 `get_hotel_price(date, room_type)`）
2. 在大模型开发者后台填写API地址并编写功能描述
3. 当用户提问时，大模型自动调用API获取数据并回复用户

**合规要求**：
- 服务器部署：阿里云或腾讯云（国内节点）
- 资质要求：完成ICP备案

#### 4.2.3 长尾服务数字化（RAG方案）

**数据采集**：
- 极简数字化：让服务商（导游、手艺人等）发语音或拍视频
- AI处理：接入语音转文字（ASR）和视觉识别模型
- 自动转化：老张语音"俺这里周三周五有空，带人上山收200块" → 结构化数据 `{Service: "Guide", Price: 200, Available: ["Wed", "Fri"]}`

**检索增强生成（RAG）**：
1. 检索：在向量数据库中检索匹配的服务商向量
2. 生成：将相关信息"喂"给大模型生成推荐回答

### 4.3 去中心化技术选型
