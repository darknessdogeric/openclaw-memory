## 建议 1 · AI 三模块合并（原模块 3 + 4 + 8）

### 1.1 Eric 判断的技术验证

原方案三个 AI 相关模块的技术栈**完全同构**：

| 技术组件 | 模块 3 AHL 平台 | 模块 4 客户雷达 | 模块 8 政策雷达 | 同构性 |
|---------|--------------|--------------|--------------|--------|
| **数据采集层** | PMS/CRM/小程序接口 | OTA API + 搜索数据 | 政策文件爬取 | ✅ 同一抽象 |
| **NLP 语义解析** | Agent 意图理解 | 搜索意图识别 | 政策文本结构化 | ✅ 同一能力 |
| **标签体系** | 客群标签 | 需求标签 | 政策适用标签 | ✅ 同一设计 |
| **匹配推送** | Agent 决策 | 需求→酒店匹配 | 政策→项目匹配 | ✅ 同一引擎 |
| **可视化仪表盘** | 管理视图 | 需求画像看板 | 政策机会看板 | ✅ 同一前端 |
| **大模型底座** | DeepSeek 本地微调 | DeepSeek | DeepSeek | ✅ **完全共用** |

**结论**：三个模块 = **一套底座 + 三个数据源 + 三套标签**。分立建设等于重复造三次轮子。

### 1.2 合并方案

```
【模块 3 · AI 与数据中台】（唯一 AI 主模块）
│
├─ 3.1 统一底座
│    DeepSeek 本地微调部署 + Agent 框架 + 私有化部署 + 内网访问
│
├─ 3.2 应用 A：AHL 业务 Agent 平台
│    商家端 + 旅客端核心流程 + 内部办公助手
│
├─ 3.3 应用 B：客户需求洞察雷达
│    OTA/搜索引擎/社交平台搜索行为 → 需求画像 → 反哺产品与营销
│
└─ 3.4 应用 C：政策资金雷达
     政策数据库 + 匹配推送 + 申报流程管理
```

**九模块 → 七模块**：3+4+8 合并为 1，**减少 2 个模块**。

### 1.3 三种交付方式分层（这是降负荷的关键）

合并后 AI 总监仍是 1 人，负荷怎么办？答案是**三个应用交付方式不同**：

| 应用 | 交付方式 | AI 总监投入 | 依据 |
|------|---------|------------|------|
| **3.1 统一底座** | 🔴 自建（亲自管）| 60% | 核心资产，必须自己掌控 |
| **3.2 AHL 平台** | 🟡 自建 + 外部共建 | 25% | 原方案已定"引入民营科技企业共建" |
| **3.3 客户雷达** | 🟢 **外部数据合作为主** | 10% | OTA 数据不自建，走数据合作/采购 |
| **3.4 政策雷达** | ⚪ 现有人员兼运营 | 5% | 原方案已定"不单独设岗" |

> 📌 **前提**：客户雷达的数据源**不自建**。原方案写的是"引入具有 NLP 意图识别、用户行为分析能力的民营科技企业，共建"——**这个前提在合并后必须坚持**，否则 1 个人干 3 套系统会崩。

### 1.4 预算调整

| 项 | 原方案 | 合并后 | 变化 |
|----|--------|--------|------|
| 政策数据库搭建 | 5 | — | 并入底座 |
| AI 追踪分析（政策）| 5 | — | 并入底座 |
| 客户扫描雷达增量 | 3.5 | — | 改为外部数据采购（走差旅/咨询或另议）|
| **AI 中台底座 + 三应用配置** | （原 AHL 35）| **35 + 6 = 41** | **+6**（三应用配置与标签体系设计）|
| 外部数据合作费 | — | **2.5** | 客户雷达数据采购（从客户雷达 3.5 + 政策雷达结余中列）|
| **信息化支出合计** | **48.5** | **43.5** | **-5** |

> 相比原方案 48.5 万 → **43.5 万，净省 5 万**。省下的 5 万建议**回投到模块 2 新媒体矩阵**（见建议 5），预算总额仍控在 215 万内。

### 1.5 ⭐ 战略收益：化解请示 8 的权责矛盾（最重要的一条）

原方案请示 8 请求"确认国堰试点数智化穿透与石基方案的业务协同对接机制"。这个请示的隐患是：**集团 IT 部门会问——"产业发展部为什么要自己做 AI 平台？"**

| | 原方案表述 | 合并后表述 |
|---|----------|-----------|
| 部门定位 | 建三个 AI 系统 | **建集团 AI 中台的酒店业应用层** |
| 与 IT 部门关系 | 潜在竞争 | **上下层互补** |
| 呈报话术 | "我们要投 48.5 万做信息化" | **"我们承接石基之上的 AI 应用层，不重复建设底层"** |

**判断**：这一条比省 5 万钱重要得多。**合并后部门在集团信息化格局中的位置从"竞争者"变成"应用层伙伴"**，请示 8 的阻力大幅下降。

## 建议 3 · 三岔湖天府山庄：从"IP 素材"升为"独立盘活标的"

### 3.1 9-10 月新增事实

| 时间 | 事件 |
|------|------|
| 2026-09-18 | 邹总赴成都东部新区调研，对接**三岔湖 80 亩三个岛屿**存量物业，探讨联合投资打造高端度假品牌 |
| 2026-09-03 | 中旅酒店与安逸交流，涉三岔湖联合开发讨论 |
| 2026-08-07 | 三岔湖天府山庄资产踏勘暨存量盘活沟通会 |

### 3.2 资产实况（方案仅当"IP 素材"处理）

| 维度 | 实况 |
|------|------|
| 位置 | 成都东部新区三岔湖水域 |
| 用地 | **88.81 亩**（6/7/107 号三地块）|
| 建面 | 地上 5122.99 ㎡ |
| 区位 | 距成都 75 分钟 / 简阳 55 分钟 |
| 股权 | **省旅投 100% 持股**（非安逸资产）|
| 已知问题 | ① 政策+规划限制资产价值 ② 两艘船舶被要求停航 ③ 供水排污不达标（无市政管网）④ 违规搭建 |
| 历史质疑 | 党委书记批评"三岔湖岛上的人在哪儿上班我们都不知道" |

### 3.3 建议

**原方案把三岔湖写成国堰文创改造的"核心 IP 之一"**——但这是两个不同性质的事：

| | 国堰 | 三岔湖天府山庄 |
|---|------|--------------|
| 性质 | **存量酒店改造** | **闲置资产盘活 / 载体运营** |
| 权属 | 安逸（经营权） | **省旅投 100%**（产权）|
| 核心动作 | 定位策划 + 改造深化 | **解绑 → 规划 → 盘活 → 联合投资** |
| 难度 | 中 | **高**（4 个硬约束问题）|
| 归口 | 产业发展部可主导 | **需集团层面授权** |

**建议**：新增"东部新区 · 三岔湖项目"工作线（2027 暂不列支，列为项目储备 + 前期研究），并在方案中**明确"产业发展部提供产业策划与品牌方案，不承担产权处置"**的边界——因为产权在省旅投，产业的只有想法。

> 💡 **提示**：三岔湖的 4 个硬约束（政策规划、船舶停航、供水排污、违规搭建）是**尽调前置问题**，任何策划方案都必须在这些问题解决路径明确之后才能出方案，否则是空中楼阁。建议 2027 年先做**合规与规划可行性研究**（约 15-20 万，可列 2027 或申请专项）。
