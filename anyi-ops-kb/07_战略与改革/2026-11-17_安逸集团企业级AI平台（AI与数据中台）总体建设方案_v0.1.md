## 〇、结论先行：对「云端租赁服务器 ＋ 本地化微调大模型 ＋ AGENT 开发」的三处修正

Eric 的初始设想方向对，但三处顺序需要倒过来，否则钱会花在错误的地方。

### 修正一：算力要拆成两件事 —— **训练用云租，推理看负载曲线**（结论：云租是对的，且优于自建）

「本地化」与「云端租赁」不是反义词，而是**两件事的两个答案**：

- **微调训练**：天然是脉冲式负载（一个模型训一次几小时），且吃数据。**→ 云租，按需付费，无 CapEx。** 2026-11 公开挂牌价：RTX 4090 24G 单卡时租 ¥1.0–2.5/小时、包月约 ¥600–900；A800 80G ¥5.5–8.0/小时；H20 96G ¥6.2–8.0/小时。7B/8B 模型一次 QLoRA 微调（2–6 小时）≈ ¥5–13/次，32B QLoRA（需 48G/80G，6–20 小时）≈ ¥20–125/次。**微调的算力费用几乎可以忽略，真正的成本在标注与评估，不在卡时。**
- **推理服务**：取决于负载曲线。内部办公负载是**白班脉冲**（9 小时工作时段，利用率约 37.5%），此时云租包月（约 ¥700/月／4090，年 ¥8,400）**远优于**自建（3 万元 CapEx 三年折旧 + 运维，年 ¥2–3 万）；只有当平台转为 **7×24 对外服务**（利用率抬到 60% 以上）时，自建才在纯经济账上打平，且换来数据不出内网与 SLA 自主。

> **决策规则（写进方案，作为触发式管理）**：
> ① 训练/微调/离线批处理 → **一律云租**；
> ② 内部办公推理 → **云租优先**，但敏感数据场景必须落到内网（见 §3.6、§4.5）；
> ③ 对外 7×24 服务的连续负载超过 **60% 利用率** 连续 3 个月 → 触发自建/包年整机评估。
> ④ 任何自建机房方案须先过本节的 TCO 算式，**不预设"自建=安全=正确"**。

### 修正二：微调不是起点，是终点 —— **内部办公的收益来自 RAG ＋ 工作流，不来自微调**

- 内部办公场景（写材料、查制度、出纪要、生成报表）的能力瓶颈是**知识检索**和**系统对接**，不是模型智力。把集团已有的制度、KB、酒店经营报告丢进 RAG，配合现成 Agent 平台（见 §6），**两到三周就能出可用的东西**；而微调需要高质量标注数据，安逸目前**没有**这类数据集。
- 安逸手上的语料（SOP、制度、合同、经营报告、复盘）是 **RAG 的原料，不是微调的原料**。硬拿它去微调，训出来的是"更像我们的幻觉"。
- 微调真正该用的四个位置（§5.4）：① 收益管理等领域算法（已立项 AI-RMS）② 高频窄任务分类/抽取（降本）③ 用大模型产出蒸馏小模型（把 80% 流量从贵模型上摘下来）④ 多模态/OCR 等专有格式适配。

### 修正三：**内部自用是"省钱"，不是"赚钱"** —— 盈利必须走对外，且要有内部结算价

- 内部办公提效、省下的工时和成本，在集团会计上是**成本节约**，换不来独立预算，也换不来"盈利能力"这个标签。
- 真正的盈利来自把安逸自用的能力**产品化对外卖**：安逸的资产是——103 家在营酒店、委托管理酒店网络、品牌与产品标准、会员与直销流量、供应链集采、**以及已建成的行业 Know-how 与数据**。
- AI-RMS 请示已写入第一笔对外收入机制：**轻资产收益管理服务费按受托项目营业收入 1.5%–2% 计取**（【集团已定】，2026-11-05 请示）。本方案要做的，是把这条单线扩成**产品矩阵**，并补上"内部需求不得挤占对外产能"的机制（§9.3）——这是内部自用型 AI 平台最常见的死法：内部用爽了，对外卖不动。

## 三、总体架构：四层 + 三条红线

### 3.1 架构总览（文字版；配图见同目录 PNG）

```
┌─ L4 应用层 ───────────────────────────────────────────────────────────┐
│  内部办公        │ 内部业务           │ 对外产品              │ 门店侧    │
│  制度问答/写作/纪要 │ AI-RMS/经营分析会助理 │ 收益能力包/AHL/网关+AI │ 智能网关+机器人 │
├─ L3 Agent 运行时层 ─────────────────────────────────────────────────┤
│  Agent 编排 │ 工具与系统集成(MCP) │ 知识库(RAG+图谱) │ 记忆 │ 评估回归 │ 审计日志 │
├─ L2 模型层（双轨 + 路由器）──────────────────────────────────────────┤
│  商用 API 轨（复杂推理/长文/代码）  ←→  私有模型轨（敏感/高频/批量）    │
│  路由规则：敏感度 × 难度 × 成本 × SLA                                │
├─ L1 算力层 ──────────────────────────────────────────────────────────┤
│  云租GPU（训练/离线/峰值）  │ 内网推理节点（敏感/对外SLA）  │ 边缘（酒店网关） │
└──────────────────────────────────────────────────────────────────────┘
         横向贯穿：身份与权限（统一账号/三级权限） · 数据分级 · 成本计量 · 日志与审计
```

### 3.2 L1 算力层

| 用途 | 方案 | 规模建议【我方暂估】 | 理由 |
|---|---|---|---|
| 微调训练 | 云租 4090/5090 24–32G、A800 80G | 间歇使用，无常驻 | 脉冲负载，按需付费，单次成本 ¥5–125 |
| 离线批处理（标注、清洗、批量抽取、夜间报表） | 云租，同上 | 夜间窗口 | 白班 GPU 闲置，夜间批处理可填谷 |
| 内网推理（敏感数据） | 内网节点，初期 **1 台 4090 级**（或云租"整机独享/租户隔离"实例） | 起步 1 卡，按 §4.3 触发条件扩容 | 数据不出内网是 AI-RMS 请示的既定约束 |
| 对外 7×24 服务 | 同上 + 水平扩展 | 利用率 >60% 触发评估 | §4.1 决策规则 |
| 门店边缘 | 依托智能网关项目（已立项 11-16） | — | 不重复建设 |

### 3.3 L2 模型层：双轨 + 路由器

- **商用 API 轨**：复杂推理、长文档、代码、多模态。优势是能力与免运维；**限制**：数据出内网、单点依赖、无模型资产沉淀。
- **私有模型轨**（开源权重，模型与算法资产归集团，符合 AI-RMS 请示既定路线）：主选 **Qwen3 系列**（中文与行业语料适配好、许可可商用），14B/32B 级 AWQ/FP8 量化单卡可跑；**DeepSeek 系开源权重**可作为强推理备选。优势是数据不出内网、权重与脚本可归档移交可审计；限制是需要运维与显卡预算。
- **路由器**（这一层是全平台省钱的核心，见 §5.2）：按 **敏感度 × 难度 × 成本 × SLA** 四因子打分，决定"走哪一轨、调哪个模型"。

### 3.4 L3 Agent 运行时层（企业级六件套）

| 组件 | 选型倾向 | 说明 |
|---|---|---|
| Agent 编排/低代码平台 | **不自研**，用成熟平台（Dify / FastGPT / n8n / Coze 等） | 自研框架是本项目最不该花的钱 |
| 工具与系统集成 | **MCP 化**：OA、PMS/CRS、财务、合同、BI、CRM 逐个封装为工具 | 自研重点（§6.4） |
| 知识库 | 沿用 AnYi-KB / anyi-ops-kb，加向量库 + 图谱 | 已有 40+ 目录资产，是最快见效的弹药 |
| 记忆与上下文 | 按 Agent 域划分会话与偏好 | 避免跨部门串味 |
| **评估与回归** | 每个 Agent 必须配评估集与回归流水线 | 缺这一环，Agent 上线即失控（§6.3） |
| **审计日志** | 全链路日志，留存 ≥180 天（对齐 AI-RMS 请示合规条款） | 可追溯是集团级平台的准入门槛 |

### 3.5 L4 应用层

- 内部办公：制度与知识问答、写作与材料起草、会议纪要与待办、经营数据问答与报表
- 内部业务：AI-RMS（已立项）、经营分析会助理、合同与招采条款审查、客诉与工单分派、巡检与能耗
- 对外产品：安逸收益能力包（AI-RMS + 品牌标准 + 会员流量 + 集采）、智能网关 + AI 运维一体包、AHL 平台化能力
- 门店侧：依托智能网关的客房/前台/餐饮智能化（与蜀智厨等伙伴分工）

### 3.6 三条红线（写进平台规范，不可绕过）

1. **数据红线**：按 L1/L2/L3 三级分类；L2（客人信息、员工薪酬、财务明细）不出内网；对外只输出聚合指标。
2. **权责红线**：集团/区域/店长三级权限分离；**定价与经营决策执行权不下放给模型**（沿用 AI-RMS 请示条款）；模型只出建议，人签字。
3. **审计红线**：训练语料、模型权重、提示词版本、工具调用日志、定价决策日志全部归档 ≥180 天，可审计、可移交。

> 来源：各平台 2026 年公开报价与第三方比价（2026-08 整理）。**采购须以询价记录为准**（《川旅投发〔2026〕147 号》要求控制价须有市场询价记录支撑，见 §4.5 备注）。

### 4.3 TCO 算式（自建 vs 云租的盈亏平衡）

设：年运行小时 H；4090 时租 p（元/小时）；包月价 m（元/月）；自建三年 CapEx C（万元）、年运维 O（万元）。

```
云租年成本   = p × H                    （按量）或 m × 12        （包月）
自建年成本   = C / 3 + O                （直线折旧 + 运维）
平衡点 H*    = (C/3 + O) × 10000 / p
```

**代入 4090 24G、p=2.15、自建 C=3 万、O=1.5 万：**

| 情形 | H | 利用率 | 云租(按量) | 云租(包月) | 自建 | **更省** |
|---|---|---|---|---|---|---|
| 内部白班负载 | 2,250 h | 25.7% | ¥4,838 | ¥8,400 | ¥25,000 | **云租（按量）** |
| 内部白班+夜间批处理 | 4,500 h | 51.4% | ¥9,675 | ¥8,400 | ¥25,000 | **云租** |
| 对外 7×24 满载 | 8,760 h | 100% | ¥18,834 | ¥8,400 | ¥25,000 | **云租（包月）** |
| 极强合规 + 满载 + 需自主 SLA | 8,760 h | 100% | ¥18,834 | ¥8,400 | ¥25,000 | 云租包月仍省，**但数据出内网成为否决项** |

> **结论（与直觉相反，但是算式的结果）**：对集团当前规模，**自建 GPU 机房在经济上不划算，云租更优**。自建的真正理由不是省钱，而是①数据绝对不出内网 ②7×24 自主 SLA ③ 卡型换代风险自担（2026 年 GPU 迭代周期已缩到 18–24 个月）。
> **因此 Eric 的"云端租赁服务器"直觉是对的**——真正需要补的是：**哪些数据不许出内网**，以及**不出一半环境的替代方案（云上租独享整机/租户隔离实例，把物理机租下来，数据只在租户边界内流转）**。

### 4.4 决策规则（触发式，不是一次性结论）

1. 训练/微调/离线批处理 → 一律云租，按量。
2. 内部办公推理 → 云租优先，L2 级敏感数据除外。
3. 连续 3 个月平均利用率 > 60% 且 7×24 对外 SLA 承诺已签 → 做自建/包年整机专项评估（评估口径同 §4.3）。
4. 任何新增算力支出，先按 §4.3 算式过一遍，再进预算。
5. 每次采购须留存市场询价记录，作为控制价依据（对接 147 号文第二十一条）。

### 4.5 数据出内网的三个解法（按合规强度排序）

| 解法 | 数据是否出内网 | 成本 | 适用 |
|---|---|---|---|
| ① 本地小模型节点（14B/32B 量化，单卡） | **不出** | 一次性 + 运维 | 薪酬、财务、客人画像、定价 |
| ② 云上租独享整机 / 租户隔离实例 | 不出租户边界 | 按整机月租 | 中高敏感 + 高负载 |
| ③ 脱敏后上商用 API | 出（脱敏后） | 按量，最便宜 | 公文、模板、通用写作 |

> 备注：《川旅投发〔2026〕147 号》要求服务类单项 50 万元以上公开招标、限额以下可询比/竞价/谈判、招采立项方案须含控制价设定依据（市场询价记录）——**算力采购若走集团渠道，也须按此路径**。

## 六、Agent 开发栈：不自研框架

### 6.1 分层与工具选型

| 层 | 用什么 | 自研/外购 |
|---|---|---|
| Agent 编排 | 成熟低代码平台（Dify / FastGPT / n8n / Coze 等）+ MCP 工具层 | 外购/复用 |
| 模型接入与路由 | 统一网关 + 路由策略 + Token 计量 | **自研（薄层）** |
| 知识库 | 现有 KB 资产 + 向量库 + 图谱 | 半自研（复用现有资产） |
| 系统集成 | OA / PMS / CRS / 财务 / 合同 / BI 的 MCP 封装 | **自研（重点）** |
| 领域 Agent | 制度问答、经营分析会、AI-RMS 等 | **自研** |
| 评估与审计 | 评估集管理 + 回归流水线 + 日志 | **自研（必须）** |

### 6.2 企业级四件套（缺一不可）

1. **统一身份与权限**：对接集团账号体系；集团/区域/店长三级权限分离。
2. **知识库治理**：入库即标注密级与有效期；知识过期要有下线机制（否则平台会自信地引用废止制度）。
3. **审计与可追溯**：全链路日志 ≥180 天；模型权重、语料、提示词版本可归档移交。
4. **成本计量**：按部门/Agent/用户计量 Token 与算力占用，作为内部结算价的依据（§9.3）。

### 6.3 评估体系（每个 Agent 上线的准入条件）

- 每个 Agent 配 **≥50 条评估集**（真实问题 + 标准答案/判定要点）。
- 上线前跑通基线；改提示词、改模型、改知识库都要**回归**，回归不过不许发布。
- 业务验收人签字（AI-RMS 已确立"店长确认制与考核口径"，同一套逻辑扩展到所有 Agent）。

### 6.4 必须自研的（其余一律复用）

① 安逸自有系统工具层（MCP）｜② 模型路由与成本计量｜③ 领域 Agent 与评估集｜④ 合规审计（密级、留存、留痕）｜⑤ 知识治理规则。

### 9.2 与 AI-RMS 的关系

AI-RMS 是**第一件可卖的产品**，不是整个平台。本方案的作用是：让 AI-RMS 的能力**复用同一底座**，并把它打包成"安逸收益能力包"（工具 + 标准 + 流量 + 成本 + 支撑），与 AI-RMS 请示第二部分结果二完全一致。

### 9.3 内部结算价机制（防止内部吃掉对外产能）

> 这是内部自用型 AI 平台最常见的死法：**内部需求无限扩张 → 算力与人力被内部占满 → 对外交付无产能 → 收入为零。**

建议三条机制（【我方暂估】，须集团确认）：
1. **内部使用同样计价**：内部部门按 Token/算力计量记账，形成"内部成本中心"，用预算约束需求量。
2. **产能配额**：对外交付优先，内部需求按配额排队。
3. **对外项目毛利单独核算**，避免内部使用被算进对外项目的成本里。

### 9.4 一句反常识的话

**内部办公提效是"省钱"，不是"赚钱"。** 它最大的价值是**给 G3 提供可演示的样板与可复制的交付能力**，而不是现金流本身。任何以"内部降本 X 万元"为主口径去申请独立 AI 预算的提案，都会拿不到钱——因为集团自己削成本削得更狠。

算力与 API 属**年度变动成本**，应单列科目按月出量；**禁止按年一次性包干**（否则用量失控无法追责）。这与 147 号文"控制价须有市场询价记录"是同一套逻辑：单价有据、总量可见。
