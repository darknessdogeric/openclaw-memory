## 1. 机制拆解：什么是共用的，什么是分开的

```
                    ┌─────────────────────────────────────┐
                    │   TripAdvisor 统一物业库 (property)  │
                    │   同一 property ID (g-geo + d-id)     │
                    └───────────────┬─────────────────────┘
                                    │
        ┌───────────────────────────┼───────────────────────────┐
        │                           │                           │
   【共用·只存一份】            【共用·只存一份】            【按语言分层】
        │                           │                           │
   ★ 点评（review）            ★ 照片库              ★ 展示层语言筛选
     一条 = 一份数据              官方图+住客图           .cn 默认中文
     写一次两站共用              caption 可分语         .com 默认英文
     ★ 但带「原始语言」标记                              ★ 「全部语言」可切换
     ★ 机器翻译不保证全量覆盖                            ★ 未翻译的显示原文
```

## 2. ★ 裁决 ③ 的准确机制（三条实证）

### 实证 1：.cn 详情页有语言筛选器（实测原文）

同一 property `g297463-d7007456`（天阅）在 `.cn` 详情页中直接出现：

```
[280] 语言
[281] 全部语言
[285] 中文简体
[292] 中文（简体）
[303] 改进翻译
[320] 翻译：
[331] 改进翻译
[345] 翻译：
```

→ **这证明：点评池是同一份，但每条点评带「原始语言」，页面按语言分层呈现，且部分点评带「翻译：」标记（机器译文）。**

### 实证 2：机器翻译已不再全量覆盖

| 来源 | 内容 |
|---|---|
| TripAdvisor Terra 官方 API 文档 | `GET /locations/{id}/reviews` 的 `language` 参数控制返回哪些语言翻译版本，**会过滤掉没有该语言翻译的点评** |
| DataForSEO（TripAdvisor 合作数据商）| 「Tripadvisor no longer automatically translates all reviews. Instead, only some reviews are translated based on its internal selection logic, while others may remain in the original language.」|
| TripAdvisor 官方支持论坛 | 「I'm using the 'All Languages' filter. This showed all the reviews, regardless of language.」|

### 实证 3：同一 property 的描述与设施，两站语言不同

| | 同一 property `g297463-d535903`（ANYEE 花园）|
|---|---|
| **.cn 站简介** | 「宾馆位于成都市中心，地处春熙路核心地段，紧邻太古里、盐市口、天府广场商圈…地铁2、3号线Ｅ1口步行3分钟…」|
| **.com 站简介** | 「The hotel offers room service, baggage storage, and a gift shop, The property also features a sauna.」|
| **.cn 设施** | 行李寄存 · 客房服务 · 无烟酒店 · 礼品店 · 桑拿 · 洗衣服务 |
| **.com 设施** | room service, baggage storage, gift shop, sauna（同一批勾选，英文呈现）|

→ **同一份 property 记录，但长文本描述与设施呈现按语言分别存储/维护 → 这就是「物业信息两套语言」的技术根据。**

## 3. ★ 裁决 ④ 的陷阱：为什么「两边各建一份」是错的

### 错误做法（正在真实发生）

| 物业 | listing A | listing B | 后果 |
|---|---|---|---|
| **安逸·新良** | `d455955` = 556 条 / 4.6 分 / 中文名「安逸·新良大酒店」 | `d34008514` = **0 条** / 英文名「CHENGDU XINLIANG HOTEL (CHUNXI ROAD TAIKOO LI)」 | ★ 权重稀释、SEO 分裂、评分不合并 |
| **天阅** | `d7007456` = 16 条 / Skytel Hotel | `d1884916` = 3 条 / TIANYUE HOTEL (Motel) · 郫都区 | 同上 |
| **锦江宾馆** | `d304961` = 8,827 条（主楼）| 东楼 = 47 条 / 5.0 分 | 主楼与东楼本可合并 |

**★ 建两份 = 把一个资产拆成两个资产 = 点评、评分、照片、排名全部对半分。这是 TripAdvisor 上最常见也最贵的错误。**

### 正确做法（一个 property，两套语言）

```
                        ① 认领（Claim）这个 property
                                    ↓
                        ② Management Center 内编辑
                                    ↓
        ┌───────────────────────────┴───────────────────────────┐
        │                                                       │
  ③ 中文版内容                                       ④ 英文版内容
  · 物业名（中文）                                  · 物业名（ANYEE …）
  · 简介（中文长文）                                · 简介（英文长文）
  · 设施勾选（中文显示）                            · 设施勾选（英文显示）
  · 照片 + 中文 caption                             · 照片 + 英文 caption
  · 地址 / 电话 / 预订链接                           · 地址 / 电话 / 预订链接
        │                                                       │
        └───────────────────────┬───────────────────────────────┘
                                ↓
                 同一个 property ID → 两站同时生效
```

**★ 关键：②认领是前提。未认领 = 无法编辑物业信息、无法回复点评。**

## 4. ★ 五步操作链（可直接下发）

| 步 | 动作 | 站 | 成本 | 收益 |
|---|---|---|---|---|
| **1** | **认领 property**（Management Center → 申请认领）| 后台 | 零 | ★★★ 解锁编辑 + 回复权限。**ANYEE 云栖、ANYEE 康养、凯宾酒店三家未认领 → 这一步就能改** |
| **2** | 填**中文版**物业信息 | .cn 呈现 | 低 | 中文客 + 国内 OTA 导流的基础 |
| **3** | 填**英文版**物业信息 | .com 呈现 | 低 | ★ 国际客与 Google 信息卡的可见性。**同一个 property 内填，不是新建** |
| **4** | 回复点评（一次回复，两站都显示）| 两站 | 中 | ★ 回复率是排序权重因子 |
| **5** | **分别引导中/英文点评** | 两站 | 中 | ★ 见 §5 —— 这是唯一需要「两边分别做」的动作 |

**★ 前四步是「一次投入、两站生效」；只有第 5 步是两站分开做的，因为要引导的是不同语言的住客。**

## 5. ★★ 最关键的运营推论：中文点评也是国际资产，但需「翻译兜底」

### 5.1 好消息：语言不参与排序权重

TripAdvisor 排名算法考量**点评数量 / 质量 / 新鲜度**，**不区分语言**。
→ **中文点评同样为 .com 的排序与排名贡献权重**（对排名而言，中文点评与英文点评等值）。

### 5.2 坏消息：中文点评在 .com 上的可见性没有保证

- 机器翻译**不再全量覆盖** → 部分中文点评在 .com 上**只显示原文**（英文读者看不懂）
- Terra API 按 `language` 过滤 → 无对应翻译的**直接不返回**
- 中文站在 .cn 上默认显示「中文简体」→ 英文点评在 .cn 上同样面临可见性问题

### 5.3 ★ 所以「两边都要上」的真正含义

> **如果只把物业信息做成中文、只引导中文点评，那么在 .com 上这家店对国际客 = 一家「没有英文内容、点评看不懂」的店 → 国际流量基本为零。**
> **反之，如果英文内容做全了，中文点评的「翻译漏出」只是可见性问题，不影响排序权重 —— 也就是「中文点评照样帮你在 .com 上打排名」。**

### 5.4 由此得出的三条具体动作

| # | 动作 | 为什么 |
|---|---|---|
| 1 | **英文描述必须写完整**（不是中文直译，要按国际客关心点重写：位置、早餐、洗衣、机场/车站距离、英文客服）| ★ `.com` 上目前花园的英文简介只有一句设施罗列，**远低于中文版信息量** |
| 2 | **主动引导英文/国际语言点评**（住客来源国语言匹配、英文离店问卷、国际客回访邮件）| 唯一能保证 .com 有可读内容的方式。**对天阅这类「外宾占 30%」的店尤其关键** |
| 3 | **定期检查「翻译」覆盖情况**（在 .com 端用「All Languages」筛选核对中文点评是否可读）| 翻译漏出 → 英文客看到乱码 → 差评风险 |

## 6. ★ 结论：两份「都做」的清单

| 维度 | 要不要「两边都做」 | 准确说法 |
|---|---|---|
| **物业是否要出现在两站** | ✅ **要** | 一个 property，两个前端自动都有 |
| **认领** | ✅ **要**（一次） | 未认领则完全无法运营 |
| **物业描述** | ✅ **要双语言** | 同一 property 内填中英两版，**不是建两个 listing** |
| **设施 / 照片** | ✅ **要双语言** | 勾选与 caption 分语 |
| **点评** | ✅ **要**（写一次两站共用）| 一个池 |
| **回复点评** | ✅ **要**（一次回复两站都显示）| |
| **邀评** | ✅ **要，且必须分语言两套动作** | ★ 唯一真正需要分开做的 |
| **英文品牌名** | ✅ **要统一** | 现状 6 种写法（ANYEE/Anyee/Anyue/An-e/Anyi/Anyi 158 Chain）→ 收敛为 1 种 |

**★ 一句话收口**：
> **点评是池，两站共用一次；物业信息是一个 property、两套语言；只有「邀评」才真正需要分两边做两套动作 —— 而恰恰这一层最容易被忽略，因为它没有后台按钮，只有一线员工在离店时的那句「方便的话帮我们写个评价」。**
