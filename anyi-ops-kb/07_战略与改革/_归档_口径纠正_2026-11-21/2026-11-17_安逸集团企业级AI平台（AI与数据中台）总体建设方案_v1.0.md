## 〇、判断摘要

### 0.1 Eric 的想法：方向成立，但有四处要改

| # | 原始设想 | 本稿判断 | 改动要点 |
|---|---|---|---|
| 1 | 云端租赁服务器 | ✅ **成立，且优于自建** | 2026-11 实价：自建 GPU 年成本 ¥2–3 万 vs 云租包月年 ¥0.84 万。真正的问题不是"租还是买"，而是**哪些数据不许出内网**——解法三档：内网最小节点 / 云上裸金属与 TEE 独享实例 / 脱敏后上 API |
| 2 | 本地化微调大模型 | ⚠️ **半成立** | 微调不是起点是终点：内部办公瓶颈是知识检索与系统对接（RAG＋工作流）。微调只用于四处：领域算法、蒸馏降本、窄任务、格式适配。**且"本地部署"不等于"数据在集团手里"**——共享 GPU 实例的数据仍在服务商侧 |
| 3 | Agent 开发 | ⚠️ **要自建的不是框架** | 框架用成熟产品（集团已有 OpenClaw 实例可作已部署样板）。必须自建的是：**工具层、领域 Agent、评估集、审计与安全运行时** |
| 4 | 满足内部办公 + 功能延伸 + 带来盈利 | ✅ **成立，但三条线的钱不是同一笔钱** | 内部办公是**成本节约**，功能延伸是**能力沉淀**，盈利只能来自**对外收费**（轻资产分成 + TOKEN 服务 + 生态抽佣）。三条线必须分账核算 |

### 0.2 与 DeepSeek 那三轮沟通的对照（三点采纳、两点修正）

DeepSeek 的核心结论是"混合架构 + Agent 运行时安全是真风险 + 云租可行 + token 计费在极高用量下才与自建打平"。**我把这套结论接住了，并补三点安逸专属的东西。**

**采纳 ① — 分域混合（直接采用为 L2 层路由规则）**

| 域 | 部署位置 | 安逸对应场景 |
|---|---|---|
| 核心敏感域 | 内网私有节点 / 云上裸金属与 TEE 独享实例 | 薪酬、财务、客人画像、定价与合约 |
| 通用生产力域 | 商用 API（经企业级网关） | 公文、纪要、模板、公开信息检索 |
| 实验与拓展域 | 云端优先，快速迭代 | 新能力原型、非敏感创新 |

**采纳 ② — Agent 运行时安全是准入门槛（升格为第四章）**
自建 Agent 把攻击面从"数据存储"扩展到"自主行动"：提示词注入、工具滥用、记忆投毒、Agent 冒充、权限提升、MCP 服务端被攻陷、工信部对 OpenClaw 类产品提示的**插件供应链攻击与内网横向渗透**。→ 转为**七条硬门槛**（§4.2），不达标不许上线。

**采纳 ③ — 成本交叉点**
"月 token 消耗达几百亿级、API 月账单 3 万+ 才与自建打平"——与本稿 v0.1 独立测算结论一致（自建推理年成本 ¥0.8–2.5 万，已接近 API 年成本）。**两套独立测算指向同一结论，这条可以拿去说服集团。**

**修正 ① — "自己搭建 AGENT"是把钱花错地方**
框架是开源商品，不是壁垒。安逸的壁垒在**行业数据与集成深度**：PMS/CRS/财务/合同/BI 的工具封装、收益管理算法、47+ 项酒店经营指标与 SOP 知识、评估集与审计规则。自研框架＝拿 6 个人的编制去买一个 GitHub 上有的东西。

**修正 ② — "本地部署 = 安全"不成立**
若没有 MLOps 与安全工程能力持续承接运行时责任（推理引擎漏洞、插件供应链、权限边界、操作审计），**全本地反而比受管控的云端更不安全**——把安全负担从有专业团队的服务商转移给一个能力有限的内部团队。→ 结论：**编制里必须补安全/运维角色（Q4），否则本地化方案在安全上是空头支票。**

### 0.3 本稿新增的四个东西

1. **价值锚**：用截至 2026-11-16 的真实酒店经营数据，算出 AI 的**可争价值池**与平台 ROI（§2）。
2. **投资明细**：首年具体金额、三年 TCO、逐项预算（§9）。
3. **TOKEN 计量计价体系**：双层计量、AIP 单位、三档价目表、单店账单示例、合规结算路径（§7）。
4. **平台生态机制**：把"一家一家谈"变成"一次接入"——统一协议、能力市场、信号共享、TOKEN 钱包与自动分成（§8）。

## 二、价值锚：旗下酒店经营基线与 AI 价值池

### 2.1 数据口径（先说清楚，避免后面算错）

**来源**：集团旗下酒店经营看板（时间维度 2026-11-16，同比年份 2025）＋明细表 40 家门店。

| 指标 | 数值 | 同比 | 环比 |
|---|---|---|---|
| 总营收 | 465,371,624.02 元 | **+0.74%** | +12.41% |
| 客房收入 | 158,345,063.65 元 | **+12.37%** | — |
| 餐饮收入 | 275,485,441.69 元 | +2.12% | — |
| 会议收入 | 18,989,355.63 元 | **+29.85%** | — |
| 其他收入 | 9,519,494.90 元 | +7.02% | — |
| 出租间夜 | 960,107.50 | +6.02% | — |
| 平均房价 ADR | 286.93 元 | +7.68% | — |
| 出租率 | 52.13% | +3.53% | — |
| 客房 RevPAR | 150 元 | +4.00% | — |
| 总额 RevPAR | 253 元 | +1.61% | — |

**口径判定（本稿按"年内累计"处理）**：以 960,107.50 间夜 ÷ 40 店 ÷ 334 天 ≈ 72 间夜/店/天，除以出租率 52.13% 反推 ≈ **138 间/店**——与集团门店规模吻合；若按"单月"解读则反推出 1,486 间/店，明显不合理。**故认定为 2026-01-01 至 2026-11-16 累计口径，年化系数 365/334 = 1.0928。**

> ⚠️ **两处口径缺口（须核）**：① 明细表仅 **40 家**，而集团在营口径为 **103 家**（AI-RMS 请示），差额部分未进本看板，**本稿一切测算均为 40 家口径，集团口径按比例外推会高估，须以 103 家实际数据复核**；② 本表为**直接经营口径**，**委托管理店与品牌授权店未包含**——而这恰恰是生态扩面（§8）的起点。

**年化（40 家口径）**：总营收 ≈ **5.09 亿元**｜客房 ≈ **1.73 亿元**｜间夜 ≈ **104.9 万**。

### 2.2 AI 价值池测算（口径：40 家）

| 情景 | RevPAR 提升 | 年客房增收 | 说明 |
|---|---|---|---|
| 保守（首年承诺档） | +3% | **≈ ¥519 万** | 行业 AI 收益管理平均 +10%~15%（AI-RMS 请示），首年打折逼近 |
| 基准 | +5% | ≈ ¥865 万 | |
| 行业对标（不承诺） | +10% | ≈ ¥1,730 万 | 全行业采用 AI RMS 后的 RevPAR 平均提升区间下限 |

**被低估的第二池子：会议收入同比 +29.85%**，年化约 ¥2,075 万。会议型收益管理（宴会与团队客的定价与撮合）在传统收益管理里几乎不做，**这是 AI 最容易做出差异的地方**，且单价高、决策链短。

**结论**：40 家口径下，**AI 首年可争价值池 ≈ 500–900 万元**（保守到基准）。

### 2.3 平台成本对比 ROI（首年）

| 项 | 金额 |
|---|---|
| 平台首年总投入（建设 + 人力，见 §9） | **¥248 万** |
| 首年可争价值池（保守 / 基准） | ¥519 万 / ¥865 万 |
| **集团侧 ROI** | **2.1 倍 / 3.5 倍** |

> 这才是这个项目最硬的一句话：**集团自己 40 家店，一年就能从 AI 上拿回 2.1–3.5 倍于平台投入的经营收益**——即便一分钱外部收入都没有，这笔账也成立。对外收入是第二层。

## 三、总体架构（生态版）

### 3.1 架构总览

```
┌─ L4 应用层 ──────────────────────────────────────────────────────────────┐
│ 内部办公        │ 内部业务            │ 对外产品（收费）      │ 生态伙伴能力    │
│ 制度问答/写作/纪要 │ AI-RMS/经营分析会助理  │ 收益能力包/网关+AI/包席 │ 需求预测/订单/内容 │
├─ L3 Agent 运行时层 ──────────────────────────────────────────────────────┤
│ Agent 编排 │ MCP 工具层(OA/PMS/CRS/财务/合同/BI) │ 知识库(RAG) │ 记忆      │
│ ★ 安全运行时：沙箱/白名单/审批熔断/供应链管控/全链路审计(≥180天) │ 评估回归 │
├─ L2 模型层（分域 + 双轨 + 路由器）────────────────────────────────────────┤
│ 敏感域：内网私有节点 或 云上裸金属/TEE 独享实例  ←→  通用域：商用 API 轨   │
│ 路由器：敏感度 × 难度 × 成本 × SLA  →  私有 Qwen3-14B/32B ｜ deepseek ｜ Qwen3 Max │
├─ L1 算力层 ──────────────────────────────────────────────────────────────┤
│ 云租 GPU：训练(QLoRA) + 离线批处理 + 峰值 │ 内网最小推理节点 │ 门店边缘(网关) │
└───────────────────────────────────────────────────────────────────────────┘
        横向贯穿：统一身份与三级权限 · 数据分级 · ★TOKEN 计量与结算钱包 · 成本计量 · 审计
```

### 3.2 与上一版不同的两个新增层

**① 生态层（新增，位于 L4 上方）**
平台不只是"集团内部的工具"，而是一个**能力供给与结算平台**。四类生态角色以标准协议接入（§8）。

**② TOKEN 计量与结算钱包（新增，横向贯穿）**
这是把"能力"变成"可交易品"的关键组件：每一次模型调用、每一次工具调用、每一次检索都计量为 TOKEN 权益，存进参与方的 **TOKEN 钱包**；平台按月对账并自动分成。**没有这层，"产业联动"只能靠人情；有了这层，联动才能自动结算。**

### 3.3 三条红线（延续并强化）

1. **数据红线**：L1/L2/L3 三级分类；客人信息、薪酬、财务明细不出内网（或不出租户边界）；对外只输出聚合指标。
2. **权责红线**：集团/区域/店长三级权限分离；**定价与经营决策执行权不下放模型**——模型出建议，人签字。
3. **审计红线**：语料、权重、提示词版本、工具调用、定价决策与 **TOKEN 计量原始记录**全部归档 ≥180 天，可审计、可移交。

## 四、Agent 运行时安全（准入门槛）

> 本章不是"风险提示"，是**上线许可清单**。任何 Agent 未通过七条门槛，不得进入生产环境。

### 4.1 为什么这块比"模型放哪儿"更重要

自建 Agent 让模型从"说话"变成"动手"，风险性质改变：

- **提示词注入**：恶意内容进入检索源或用户输入，劫持工具调用。
- **工具滥用与权限提升**：Agent 被诱导调用高权限工具（改价、发函、删数据）。
- **记忆投毒**：跨会话写入污染长期记忆。
- **MCP 服务端被攻陷**：工具层是最新的攻击面。
- **插件/技能包供应链攻击**：工信部已就 OpenClaw 类产品发布风险提示，明确**插件供应链攻击与内网横向渗透**为主要风险。
- **长时运行 Agent 的累积副作用**：一次错误动作被放大成一批。

### 4.2 七条上线门槛

| # | 门槛 | 验收方式 | 责任 |
|---|---|---|---|
| 1 | **独立网段隔离**：Agent 运行环境与关键生产系统隔离，禁止非必要跨网段访问 | 网络拓扑图 + 渗透测试报告 | 安全 + IT |
| 2 | **最小权限 + 目录白名单**：专用低权限账户运行；文件访问目录白名单；禁管理员与跨目录访问 | 权限矩阵 + 越权测试用例 | 安全 + 平台组 |
| 3 | **高危操作人工审批 + 熔断**：删除、外发、改配置、改价必须二次确认；单日操作量超阈值自动熔断 | 熔断演练记录 | 平台组 + 业务 |
| 4 | **全链路审计**：操作与运行日志完整留存 ≥180 天，可追溯到人、到 token、到工具 | 日志抽查 + 留存策略核验 | 平台组 |
| 5 | **供应链管控**：只使用经审批的官方组件与技能包，禁止未审计第三方插件 | 技能包白名单 + 审批台账 | 平台组 |
| 6 | **提示词注入防护**：检索源清洗与可信度标注、输入输出过滤、工具白名单、异常行为检测 | 注入测试集（≥30 条）回归 | 平台组 |
| 7 | **可回滚与人工接管**：任一 Agent 可一键停用并回退到人工流程 | 停用演练记录 | 平台组 + 业务 |

### 4.3 一个必须说清的判断

**「本地部署 = 安全」是伪命题。** 若集团没有持续承接运行时安全责任的 MLOps 与安全工程能力，全本地方案在安全上反而更不安全——因为把专业服务商的防护责任转嫁给了能力有限的内部团队。
→ **所以编制里必须有安全/运维角色（Q4 缺口岗）。本地化买到的是"数据不出域"，不是"自动安全"。**

> 集团已具备一项别人没有的优势：**已经有在跑的 OpenClaw 实例（B166ER 本身）**。它可以当作**已部署的 Agent 运行时样板**——安全门槛七条直接在生产环境里迭代，而不是在白纸上设计。

| 卡型风险 | 平台承担 | 平台承担 | 自担（迭代周期已缩至 18–24 个月） |

**本稿选择 B 为主 + C 的最小形态作为补充**：
- **训练与批处理**：云租按量（B 方案即可，语料脱敏后上传）。
- **敏感域推理**：内网 **1 张起步卡**（自建最小节点，CapEx ≈ ¥1.5–2.5 万，不进机房自建），保证 L2 数据绝对不出内网。
- **对外 SLA 与高负载**：云上裸金属/TEE 独享实例；若连续 3 个月利用率 > 60%，触发自建专项评估。

### 5.3 TCO 算式与决策规则

```
云租年成本 = 包月价 × 12（或 时租 × 年运行小时）
自建年成本 = 硬件 CapEx / 3 + 机房与运维
平衡点：年运行小时 H* = (CapEx/3 + 运维) × 10000 / 时租
```

**代入 4090 24G、时租 ¥2.15、自建 CapEx ¥3 万、运维 ¥1.5 万**：平衡点 H* ≈ 5,581 小时/年 ≈ **利用率 64%**。

| 情形 | 利用率 | 云租（包月） | 自建 | 更省 |
|---|---|---|---|---|
| 内部白班负载 | 26% | ¥8,400 | ¥25,000 | **云租** |
| 内部 + 夜间批处理 | 51% | ¥8,400 | ¥25,000 | **云租** |
| 对外 7×24 满载 | 100% | ¥8,400 | ¥25,000 | **云租（但数据出内网成为否决项）** |

**决策规则（触发式）**：
1. 训练/微调/离线批处理 → 一律云租按量。
2. 内部推理 → 云租优先；**L2 敏感数据 → 内网最小节点**。
3. 连续 3 个月平均利用率 > 60% 且已签 7×24 对外 SLA → 触发自建评估（口径同上式）。
4. 任何新增算力支出，先过此算式再进预算；**采购留存市场询价记录**（《川旅投发〔2026〕147 号》第二十一条对控制价依据的要求）。

## 六、模型层与 TOKEN 成本基线

### 6.1 三档模型与分工

| 档 | 模型 | 单价（USD/百万 tokens，2026-11-17） | 折人民币/万 tokens | 用在哪 |
|---|---|---|---|---|
| 便宜档 | deepseek-chat (v3.2 系) | $0.23 / $0.34–0.35 | 输入 ¥0.016 / 输出 ¥0.024 | 公文、纪要、摘要、翻译、模板 |
| 主力档 | deepseek-v3 | $0.23–0.32 / $0.93–1.10 | 输入 ¥0.017 / 输出 ¥0.078 | 经营分析、长文档、代码、复杂问答 |
| 旗舰档 | Qwen3 Max | $0.50 / $5.00 | 输入 ¥0.036 / 输出 ¥0.355 | 高价值推理（少用） |
| **私有档** | Qwen3-14B/32B 量化，自部署 | 硬件摊销 + 电费 | **≈ ¥0.001** | 制度、合同、薪酬、客人画像、定价 |

### 6.2 混合成本基线（用于定价锚）

假设流量结构 **私有轨 55% + 便宜档 30% + 主力/旗舰档 15%**，加权平均：

| 情形 | 混合成本（每万 tokens） |
|---|---|
| 敏感数据为主的场景（私有轨占 90%） | **¥0.003–0.006** |
| 一般办公与业务场景（混合） | **¥0.015–0.035** |
| 全走旗舰档（反面参照） | ¥0.10+ |

> **关键事实：TOKEN 的成本极低**（1 万 tokens 只值几分钱到几毛钱）。**这决定了 TOKEN 计价只能是"计量工具 + 变动成本回收机制"，绝不可能靠 token 费用覆盖一个企业级平台的固定成本。** 这一点必须说清楚，否则会拿着 TOKEN 价目表去做一个收不回钱的生意。

### 6.3 路由规则（省钱的核心，也是对外的成本优势）

| 任务 | 走哪一轨 | 预期成本 |
|---|---|---|
| 制度/合同检索问答、薪酬、客人画像、定价 | **私有轨（内网）** | ¥0.001–0.006/万 |
| 公文、纪要、通知、摘要 | 便宜档 API | ¥0.016–0.024/万 |
| 经营分析会材料、长文档、代码 | 主力档 API | ¥0.017–0.078/万 |
| 高价值复杂推理 | 旗舰档 | ¥0.036–0.355/万 |

**全量走最贵档 vs 正确路由：年成本差 5–6 倍**（v0.1 已算，结论不变）。

## 七、TOKEN 计量与计价体系（核心章）

### 7.1 双层计量：成本账用 tokens，结算账用 AIP

| 层 | 单位 | 用途 | 对谁 |
|---|---|---|---|
| **成本账（原始）** | **tokens**（区分 输入/输出/缓存命中/检索/工具调用） | 真实算力成本、审计、对账、路由优化 | 集团内部、审计 |
| **结算账（商业）** | **AIP（AI Point，安逸算力点）** | 对内对外结算 | 门店、委托管理店、生态伙伴 |

**AIP 定义**：**1 AIP = 10,000 tokens**（含输入与输出，缓存命中按 0.2 AIP 计，检索与工具调用按实际 token 计）。
**为什么不裸用 token**：酒店业主与供应商看不懂 token，且 token 消耗与业务价值不成正比——一份 5,000 token 的经营分析报告，价值远高于 5,000 次简单问答。**AIP 是把"算力"包装成可采购的商品单位，tokens 留在后台做成本与审计。**

### 7.2 三档价目表（本稿核心交付物之一，详见附件 xlsx）

| 档位 | 适用对象 | AIP 单价 | 相对成本倍数 | 说明 |
|---|---|---|---|---|
| **A. 内部结算价**（自营/在营店） | 集团自营与在营门店 | **¥0.15 / AIP** | ≈ ×3–×5 | 覆盖变动成本 + 平台管理费；**用于轻资产定价的成本锚** |
| **B. 合作方价**（委托管理店 / 品牌授权店） | 非自有资产的门店 | **¥0.30 / AIP** | ≈ ×6–×10 | 首年可给 **7 折渗透价 ¥0.21** 换规模与数据 |
| **C. 生态伙伴价**（供应商/渠道/内容方调用平台能力） | 生态伙伴 | **¥0.25 / AIP** | ≈ ×5–×10 | 平台抽佣 **15%**，按 TOKEN 流水结算 |

> **为什么内部价低于合作方价**：自营店的 AI 投入本质是集团内部投资，定价的目的是**透明与考核**（让门店看见成本、让集团看见真实用量）；合作方是**真收入**，必须有毛利。
> **为什么内部价不能定太低**：内部结算价一旦失真，**轻资产对外报价就失去成本锚**，产业发展部去谈轻资产时会被合作方按"你自己的成本"倒推压价。所以内部价必须能还原真实成本。

### 7.3 场景包（比 token 更签约的东西）

酒店与业主不签"token 合同"，签"**能力包**"。**TOKEN 是包内的计量与超量结算单位。**

| 场景包 | 计价方式 | 建议价（【我方暂估】，须按§7.5 价值封顶校准） | 含配额 |
|---|---|---|---|
| **收益管理增强包**（AI-RMS） | 按店/年 | **¥2–8 万/店**（= 年营收的 0.4%–1.2%） | 约 2,000–4,000 AIP/月 |
| **经营分析会助理包** | 按店/年 | ¥1.5–3 万/店 | 约 800–1,500 AIP/月 |
| **办公协同包** | 按席位/年 | ¥0.3–0.8 万/席 | 约 300–600 AIP/席/月 |
| **智能网关 + AI 运维一体包** | 按店/年（设备 + 订阅 + 运维） | ¥1.5–5 万/店 | 按设备数配 |
| **超量加购** | 按 AIP | 超出配额部分按档位单价 | — |

### 7.4 单店账单示例（可对账口径）

**示例店**：中型店，年化总营收 ¥600 万，客房占比 45%（客房年收入 ¥270 万），出租率与 ADR 取集团均值。

| 项 | 月度 | 年度 |
|---|---|---|
| 收益管理类调用（日度调价、竞品监测、预测复盘） | 300 次/日 × 3,000 tok ≈ 2,700 万 tok ≈ **2,700 AIP** | 32,400 AIP |
| 办公协同类（纪要、公文、问答） | 120 次/日 × 3,000 tok ≈ 1,080 万 tok ≈ **1,080 AIP** | 12,960 AIP |
| **合计消耗** | **3,780 AIP** | **45,360 AIP** |
| 变动成本（混合 ¥0.025/AIP） | ¥95 | ¥1,134 |
| 平台固定费分摊（场景包 ¥2.4 万 − 变动成本） | ¥1,905 | ¥22,866 |
| **内部结算额** | **¥2,000** | **¥24,000**（年营收的 **0.4%**） |
| 该店 AI 可验证价值（RevPAR +3%） | — | **¥81,000** |
| **AI 费占 AI 创造价值** | — | **30%** ✅ 在可接受区间 |

> **这张表就是定价的唯一纪律：AI 费必须显著低于 AI 创造的价值。** 超出这个比例，门店不会用、也不会续。

### 7.5 自营店 vs 管理店：**必须区分，但区分的是付费主体与结算路径，不是两套产品**

**本稿判定（Eric 委托）**：

| 维度 | 自营 / 在营店 | 委托管理店 / 品牌授权店 |
|---|---|---|
| 付费主体 | 集团（内部结算） | 合作方（真实付费） |
| 计价档 | A 档 ¥0.15/AIP | B 档 ¥0.30/AIP（首年 7 折渗透价 ¥0.21） |
| 场景包 | 按内部成本 + 管理费 10% 定价 | 场景包标价 × 1.5–2.0（合作方无内部让利空间） |
| 首年策略 | 全量覆盖，做样板与数据飞轮 | **渗透价换规模与数据**，12 个月后按标准价续约 |
| 收入性质 | 成本节约 + 内部考核 | **对外收入（真金白银）** |
| 是否同价 | ❌ **绝不同价** | ❌ |

**三条理由**：
1. **轻资产定价锚**：轻资产竞标时，合作方一定会问"你们自己一家店投多少 AI"。内部结算价失真 → 产业发展部谈轻资产时被自己的成本倒逼压价 → **内部价必须真实**，这是战略底线。
2. **集团内部考核**：内部结算让门店看得见成本、让集团看得见真实用量；这既是降本工具，也是"轻重分离"时的定价依据。
3. **真收入只能来自合作方**：内部 103 家全部免费覆盖，平台一年最多 ¥150–200 万内部结算；**平台盈利与生态价值必须来自合作方与生态伙伴**。

> **一句话结论**：**同一张价目表、三档单价、一套能力包。区分的是"谁付钱、按什么价付"，不是"给你什么功能"。**

### 7.6 计量、结算与合规路径

| 环节 | 机制 | 依据 |
|---|---|---|
| 计量点 | 模型网关（输入/输出/缓存命中）、检索（分块数）、工具调用（次）、Agent 任务（次） | 统一网关，不允许绕过 |
| 原始记录 | 每笔调用写入计量原始账（不可篡改、含调用链 ID） | 审计红线（≥180 天） |
| 账单 | 按 AIP 汇总，月度出账单；含分部门/分店/分 Agent 明细 | 内部结算与对外对账同源 |
| 对账 | 月度自动对账 + 争议申诉窗口 3 个工作日 | 对齐 147 号文异议机制精神 |
| 合同 | 内部：集团内部结算备忘；对外：服务合同（含能力清单、AIP 价表、SLA、数据与安全条款、分成） | 服务类单项 50 万以上须公开招标 |
| 采购关联 | 生态伙伴的模型/API/算力采购同样须走招采流程，留存询价记录 | 147 号文第二十一、二十二条 |

### 7.7 两条必须讲清的诚实结论

1. **TOKEN 计价天然收不回平台固定成本。** 按 §6.2，1 万 tokens 只值几分到几毛钱；即使把 40 家店与 60 家合作方的全部消耗按 ¥0.15–0.30/AIP 结算，年规模约 **¥150–260 万**，而平台固定成本（人力 + 运维 + 生态建设）约 **¥180–220 万/年**。**结论：TOKEN 费只能覆盖变动成本 + 部分固定成本，平台必须靠 ① 场景包年费 ② 轻资产营收分成 ③ 生态抽佣 三条腿走路。**
2. **单店收费必须低于其创造的价值**（§7.5 价值封顶）。所以**单店不赚钱是设计目标，不是失败**——单店的价值在于数据飞轮与轻资产样板。

## 八、平台生态：把"一家一家谈"变成"一次接入"

> Eric 的判断：**"如果集团建成了这个体系，后续任何合作方只要加入这个体系就可以实现产业联动和内外部合作，而不是像现在这样一家一家沟通、一个点一个点推。"** 本章把这句话拆成可执行的机制。

### 8.1 一次性谈不下来的三个真实原因

| 原因 | 现状表现 | 平台化的解法 |
|---|---|---|
| ① **每个合作方都要重谈能力边界** | 谈的是"你这个 AI 能干什么"，而不是"接入后自动有什么" | **标准能力包 + 能力市场**：能力清单标准化，谈判只谈商业条款 |
| ② **数据与系统各不相同** | 每家酒店 PMS/CRS 不同，接一次做三个月 | **MCP 工具层 + 适配器**：主流 PMS/CRS 做标准适配器，接入周期从月降到周 |
| ③ **钱与责任没有结算机制** | 能力白给、或私下结算、口头承诺 | **TOKEN 钱包 + 自动分成 + SLA 与责任条款**：能力可计量、账可自动结 |

### 8.2 四类生态角色与接入点

| 角色 | 接入平台的收益 | 平台的收益 | 标准能力包 |
|---|---|---|---|
| **① 酒店/物业方**（委托管理、品牌授权、加盟、拟合作） | 收益管理、智能网关运维、客诉与工单、能耗 | **数据飞轮 + 轻资产签约** | AI-RMS、网关 AI 运维、会议收益、客诉分派 |
| **② 供应商/服务商**（餐饮供应链、清洁布草、客用品、维修、机器人如蜀智厨） | **获得未来 30–90 天需求预测（脱敏聚合）**，从"被动接单"变"按需备货" | 订单密度提升、履约数据资产 | 需求预测 API、订单协同 Agent、标准 SOP Agent |
| **③ 渠道/流量方**（OTA、会员、分销、旅行社、团餐） | 价格与库存协同，减少价格倒挂，提升可售 | 渠道价格信号、会员转化 | 库存与价格建议、竞品监测、促销生成 |
| **④ 内容/营销/新零售方** | 素材生成、客群洞察、活动策划 | 消费场景数据闭环 | 内容生成 Agent、客群洞察 Agent |

> **网络效应的真正来源只有一个：需求与价格信号。** 平台沉淀"需求预测 + 价格带"这一个核心资产（已在 AI-RMS 立项范围内）。酒店接入 → 算法更准 → 预测更准 → 供应商愿意相信并按预测备货 → 供给侧数据回流 → 平台再变准。**这个飞轮一旦转起来，后加入的合作方拿到的能力显著优于先加入者——这才是"一次接入、产业联动"的护城河，而不是把 N 次谈判变成 1 次合同。**

### 8.3 一次接入的五个标准件

| 标准件 | 内容 | 谁提供 | 周期目标 |
|---|---|---|---|
| ① **统一接入协议**（主协议 + 附件） | 能力清单、AIP 价表、SLA、数据与安全条款、分成与结算、责任与退出 | 集团法务 + 产业发展部 | 1 份模板，**不逐家重谈** |
| ② **能力市场（Capability Marketplace）** | 标准能力包目录、版本、定价、调用方式、效果指标 | 平台组 | 2027 上线 v1 |
| ③ **接入手册与 SDK** | MCP 工具接入、鉴权、计量、结算、沙箱测试环境 | 平台组 | **认证周期目标 ≤ 15 个工作日** |
| ④ **TOKEN 钱包与自动结算** | 预付/后付、账单、自动分成、争议处理 | 平台组 + 财务 | 2027 试点 |
| ⑤ **合规背书层** | 等保测评、数据分级说明、审计报告模板、渗透测试结论 | 安全 + 集团 IT | 一次出具、多方复用 |

### 8.4 推广三级打法

| 级别 | 对象 | 目标 | 定价 | 时间 |
|---|---|---|---|---|
| **一级：样板与数据飞轮** | 集团自营/在营店（103 家口径，本看板 40 家） | 全量覆盖、跑出基准与评估集 | **内部结算价 A 档** | 2027 上半年 |
| **二级：规模化收入** | 委托管理店、品牌授权店、加盟与拟合作方 | **首年 30–60 家**付费接入 | B 档（首年 7 折渗透价） | 2027 下半年起 |
| **三级：产业联动与抽佣** | 供应商、渠道、内容与新零售伙伴 | 生态 TOKEN 流水 **¥500 万/年**（抽佣 15% ≈ ¥75 万） | C 档 | 2028 起 |

### 8.5 开放的风险与边界（必须写进协议）

| 风险 | 边界设计 |
|---|---|
| 数据经平台外泄 | **只开放 API，不开放模型与训练数据**；所有接入方走统一网关，计量与审计全覆盖 |
| 能力被绕过平台私下交易 | 平台保留**结算与审计唯一入口**；生态分成与结算绑定 TOKEN 钱包 |
| 伙伴能力参差，交付质量失控 | 能力包有准入与认证；未认证能力不得进入能力市场 |
| 供应商获得需求数据后自建平台 | 需求信号只以**脱敏聚合**形式发布；模型权重与语料不出平台 |
| 生态开放反噬内部数据安全 | 分级开放（能力分级 × 数据分级）；L2 数据不出内网，生态侧只出聚合结果 |

| # | 项 | 内容 | 金额（万元） | 依据 |

### 10.3 一个必须说的结构性判断

**这个平台在第一年几乎不赚钱，这是正常的，也是对的。**
- 第一年真正的产出是：**数据飞轮起步 + 样板 + 可复制的交付能力 + 轻资产谈判筹码**。
- 真正的利润拐点在 **2028 年**，来自三件事同时发生：合作方规模（60+ 店）、轻资产分成、生态抽佣流水。
- **判断标准不应是"第一年赚多少"，而应是"第二年能不能自动长出来"**——即：每新增一家合作方的接入成本是否递减、生态抽佣流水是否随接入方数量线性增长、TOKEN 计量是否让平台具备自动结算能力。**这三条是 2027 年真正的 KPI。**
