# 第一章 这是什么——AHL 不是 SaaS，是范式革命者

## 1.1 一句话定位

**AHL 是四川省国资文旅行业首个 AI 垂系 Agent 平台。**

它做的事情只有一件：**让客人用 AI 直接找到对的商家，让商家用 AI 直接找到对的客人**——中间不抽水，不抽佣，不囤数据。

## 1.2 它解决什么问题

客人今天找酒店、找景区、找特产、找餐厅的路径：

```
现状：
  客人 → 打开 OTA 平台 → 搜索 → 比价 → 看评价 → 选 → 下单 → 钱到平台 → 平台抽 10-15% → 剩 85-90% 到商家

AHL 模式：
  客人 → 对 AI 说出需求 → AI 直接匹配 → 客人下单 → 钱 100% 到商家 → 平台收 TOKEN 计量费（≈电费）
```

**0% 佣金**。客人付的钱 100% 到商家。平台只收一笔按"握手次数"算的"电表费"。

# 第二章 核心命题——为什么 AHL 是范式革命者 ⭐⭐⭐ 深化

## 2.1 行业现状：4 大旧范式并存

当前中国文旅行业有 4 种"客人-商家对接"范式，它们各有局限：

```
范式 1 · OTA 平台范式
  代表：携程、美团、飞猪
  模式：平台聚合商家 → 客人搜索 → 平台抽佣 10-15%
  优势：流量大、用户习惯成熟
  局限：客户归平台 / 数据归平台 / 定价权归平台 / 商家沦为货架

范式 2 · 传统旅行社线下范式
  代表：国旅、青旅、中旅
  模式：门店销售 → 行程打包 → 客人跟团 → 现场购销
  优势：服务标准化、有信任感
  局限：服务半径有限 / 行程固化 / 复购率低 / 客单价高

范式 3 · 自营商城/小程序范式
  代表：各品牌自有 APP、智游天府、携程"里白"AI 工具
  模式：商家自建 → 客人下载 → 商家维护 → 客人下单
  优势：客户归属商家、数据归属商家
  局限：流量封闭、转化率低、跨店协同难、需要自建技术团队

范式 4 · 国资平台间数据互通范式
  代表：智游天府、省大数据中心、各地市州政务平台
  模式：国资平台间 API 对接 → 数据共享 → 联合服务
  优势：国企背书、政策支持
  局限：接口对接成本天价 / 沟通协调无穷 / 数据标准不一 / 责任归属不清
```

**这 4 种范式有一个共同问题**：**"客人找商家"是困难的。**

## 2.2 AHL 范式——AI 双 AGENT 范式（颠覆式差异）⭐⭐⭐

AHL 是**第 5 种范式**——AI 双 AGENT 范式：

```
客人 Agent（C 矩阵）：  5 类客群 × N 个体  =  持续识别客人需求
商家 Agent（B 矩阵）：  多业态商家 × N      =  持续输出商家特点
AHL 协议层：            标准化握手协议      =  零佣金 + TOKEN 计量
数据回流：              双向流动            =  越用越准

范式 5 · AI 双 AGENT 范式
  代表：AHL（垂类 Agent 平台）
  模式：商家持续输出运营特点 → AI 自动识别 + 翻译给客人 → 客人 AI 自动匹配 → 钱 100% 到商家
  优势：客户归商家、数据归商家、定价权归商家、跨业态互导、商家被动变主动
  局限：商家需持续输出运营特点（这是 AHL 的"入场费"——但很轻）
```

## 2.4 为什么 AI 范式是"颠覆式"？三个根本原因 ⭐⭐⭐

**原因 1：自然语言 = 最低摩擦的交易形态**

```
旧范式：客人需要"会搜索"+"会看图"+"会读评价"+"会比价"
       → 决策时间 30+ 分钟
       → 转化率 5-10%

AHL：客人只需要"会说话"
     → "明天想带孩子住江景 600 左右"
     → AI 自动匹配 + 推荐
     → 决策时间 3 分钟
     → 转化率 30%+（3-6 倍提升）
```

**原因 2：商家特点 = 数据 + 运营 = 自动讲故事**

```
旧范式：商家需要"会营销"+"会写详情页"+"会做视频"
       → 商家精力消耗大
       → 持续输出难

AHL：商家只需"做好自己的事"（运营）
     AI Agent 持续识别特点
     → 自动翻译给客人
     → 自动精准匹配
     → 商家精力消耗极小
     → 持续输出自然
```

**原因 3：商家主动汇聚（核心痛点）⭐⭐⭐**

```
旧范式：数据互通需要商家主动
       → 商家不愿意（数据是命脉）
       → 平台谈判成本天价
       → 责任归属谈不拢
       → 最后不了了之

AHL 范式：商家主动汇聚
       → 商家只要做好自己的事（运营特点输出）
       → 客人匹配 + 收益分成 = 商家立刻获益
       → 不需要让渡数据所有权
       → 数据归属商家，AHL 只做"协议层"
       → 越用越准（数据厚度增加）→ 商家更主动
```

# 第三章 核心痛点——省属国企数据互通困境 ⭐⭐⭐ 深化

## 3.1 现状：省属国企平台林立，数据互通近乎不可能

**问题 1：平台数量过剩（"省级数据中台"到处都是）**

```
仅四川省内就至少有：
  ├─ 智游天府（智慧文旅）
  ├─ 川渝数藏（数字藏品）
  ├─ 天府安逸买（电商）
  ├─ 四川省大数据中心（政务数据）
  ├─ 旅投集团旗下各板块平台（酒店/景区/餐饮）
  ├─ 商投集团旗下各平台（红旗连锁/曙光汇/天府菜油）
  ├─ 各市州文旅平台（21 个市州各自一套）
  ├─ 景区/酒店自有平台（每家一套）
  └─ 携程/美团/飞猪/小红书（外部 OTA 平台）
```

**问题 2：接口对接成本高得惊人**

真实案例参考（来自普元案例库 / 厦门大数据 / 中铁案例）：

| 案例 | 对接规模 | 时间成本 | 人力成本 |
|------|---------|---------|---------|
| **中国中铁**（万亿央企）| 800+ 套系统 + 2000+ API + 日均 1800 万次调用 | 数年 | **节省 22.7 人年开发 + 23.7 人年运营** |
| **厦门大数据**（市属国企）| 12 类核心接口 + 政务/金融/交通 | 数月 → 数周 | 持续投入 |
| **某省大数据局** | 86 个委办局 | **1 年计划 → 3 个月完成** | 巨大 |
| **某国有银行** | 2400+ 接口 | 2 个月 | — |
| **上海移动** | 过亿次日均调用 | 持续运营 | — |
| **红海云（HR 场景）** | 央国企普遍痛点 | "**后续投入大量开发资源进行二次定制**" | "**既拉长项目周期也增加预算压力**" |

**问题 3：核心原因——技术架构 + 责任归属 + 数据安全**

> "**国有企业对数据安全存在顾虑，数据开放范围模糊，非涉密数据也未充分共享，缺乏统一的数据接口与安全标准**"（上海市政协委员严洁红提案）

> "**国资委的系统和国有企业的系统之间，在系统技术架构、开发语言、数据结构方面也存在较大的差异，系统之间统一数据库结构、统一指标字段很难实现，通过接口方式实现数据对接需要做大量工作**"

> "**企业需要在多个上级主管部门建立的信息化系统中重复填报数据……企业缺乏足够人员和精力填报数据，填报意愿不高**"

> "**即使各级国资委内部的不同职能部门为了完成自己的业务工作建立了不同的信息化系统，这些系统之间也没有实现数据对接、指标统一，企业需要在多个上级主管部门建立的信息化系统中重复填报数据**"

## 3.2 旧范式下的"数据互通"困境

```
传统做法：让各家平台做 API 对接

  平台 A ←─→ 平台 B
              ↕
  平台 D ←─→ 平台 C

  实际：
  ├─ 平台 A 担忧数据安全 → 拒绝开放
  ├─ 平台 B 担心责任归属 → 谈判半年
  ├─ 平台 C 技术架构不同 → 接口标准不一
  ├─ 平台 D 觉得划不来 → 消极配合
  └─ 最终 4 平台"接口"了 1 年 → 还在测试

  后果：
  ├─ 项目延期 12-24 个月
  ├─ 预算超支 200-500%
  ├─ 数据质量参差
  ├─ 责任不清扯皮
  └─ 难以持续运营
```

**这就是 Eric 16:14 反复强调的——"接口费用成本高出天际，沟通时间成本无法估量"**。

## 3.3 AHL 范式：让机构/商家主动接入 ⭐⭐⭐ 核心价值

**根本性差异**：

| 维度 | 旧范式（API 对接）| AHL 范式（价值互换）|
|------|----------|----------|
| **谁主动** | 平台/国资委要推动各家 | 商家/机构自己主动 |
| **谁受益** | 抽象的"省平台建设" | 具体的"我多卖了一单" |
| **数据归属** | 共享到平台（商家顾虑）| 归商家自己（不外流）|
| **协调成本** | 平台间谈判数年 | 商家"接不接"自动选 |
| **谁付钱** | 国资委或集团掏钱建平台 | 商家分润 + 客人 TOKEN |
| **持续性** | 一次性建设后可能闲置 | 越用越准 + 越多人用 |

**AHL 的核心价值**：

```
不是"让平台去对接"——而是"让机构/商家主动接入"

旧范式：
  平台 A 说："请把你的数据给我"
  商家 B 答："不行，这是我的核心数据"
  → 死锁

AHL 范式：
  商家 B 看到："我接入 AHL 后，客人匹配率提升 30%，GMV 涨 50%"
  商家 B 主动："我要接入"
  → 商家自己的数据不外流（AHL 只做协议层）
  → 客人付的钱 100% 到商家（AHL 收 TOKEN 费）
  → 越多人用，AI 越准，商家越多 → 正循环
```

**AHL 的"数据协议"特点**：

```
1. 数据不外流：商家的客户数据、交易数据存在商家自己
2. 计算外包：商家调用 AHL 的 AI 能力，但数据不出商家库
3. 价值分账：每笔交易按 TOKEN 消耗分账
4. 互导激励：跨业态互导 = 5-10% 分成 = 商家主动找接入
```

异化形态：
  - 房车营地（让自驾变成"移动酒店"）

## 4.2 商家持续特点输出（3 层识别机制）

3 层识别机制：

第 1 层：商家自主申报

  - 新增服务 / 设施 / 活动 / 菜品 / 路线 / 套餐的更新

第 2 层：AI 自动识别（持续 7×24）

  - 客诉工单
  - 销售数据
  - 入住/到访/购票数据
  - 员工反馈
  - 自动发现"这个酒店最近的服务特色变了" → 翻译给客人

第 3 层：客人反馈（持续学习）
  - 客人对什么感兴趣（停留时长、点击率、购买率）
  - 客人的痛点（差评、客服投诉）
  - 客人的推荐（朋友推荐、口碑传播）
```

**商家不必会做营销，只需做好自己的事**——AI 自动讲故事。

## 4.3 SKILL 矩阵（v3.3 修订）⭐

**v3.2 错误**：列了 72 个 SKILL 明细。

**v3.3 修正**：

```
SKILL = 场景化能力积木

每个 SKILL 封装一个具体能力（如"智能预订"/"收益管理"/"扫码红包"）
SKILL 可插拔可组合 → 组合成场景化解决方案
SKILL 库随业务发展持续延展
