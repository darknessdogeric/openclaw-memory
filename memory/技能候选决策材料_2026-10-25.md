### 1. 扫描的「检索通道」选错了 → 候选池 4 轮不变 vs 1 轮 81 个

| 查询 | 命中 |
|---|---|
| 「高德 酒店」 | 0 条 |
| 「高德酒店」 | 0 条 |
| 「高德」 | **10 条** |

→ 中文检索必须用 2–3 字粒度（扫描器已改 17 词）。

## 二、必须自建的能力（本市场买不到）

### 🔴 酒店竞品房价 / 动态定价监控

- **实测**：12+ 组同义词（竞品房价监控／竞对价格／动态定价／同行价格监控／competitor pricing／rate shopping／revenue intelligence…）× **双通道**（registry 关键词 + clawhub 向量）→ **酒店域 0 命中**；命中的 `competitor-*` 全是电商/商品域
- **对照组校准**：同一套判定逻辑对「酒店房价聚合」给出 20 个域内命中 → **不是判定过严，是真空白**
- **但本轮浮出 `apify-competitor-intelligence`**（装 75，跨 Google Maps/Booking.com/社交平台分析竞品定价与定位）→ **它不是「酒店竞品房价监控」，但比电商竞品监控更接近**；若其 Booking.com 侧能按城市/日期取竞对房价，**可当作取数层**（需确认 apify 额度成本）
- **结论**：核心的「竞对房价持续采集 + 异动预警」**仍需自建**；买到的只是取数与周边情报零件

### ⚠️ 一次已修正的假阳性（记录在案）
首跑时「酒店竞品房价/动态定价监控」被判 **THIN**，核心命中 = `pricing-calc` ——
但它是**通用 SaaS 产品定价计算器**，与酒店房价监控无关。
**根因**：`core_re` 里 `otel` 是 **`hotel` 的子串**、`ota` 是 `total` 的子串、`peer` 命中 "peers"
→ 已给全部拉丁短词加**词边界 `\b`** 并做正反例回归验证（`pricing-calc` core=0 ✅）。
**修正后该能力回到 ADJACENT（域内 core=无）→ 结论「市场买不到，只能自建」成立。**
**扫描器的空白差分机制当场报出了这次变化（THIN → ADJACENT）** —— 差分比绝对值更可靠。

### ⚠️ 结论修正（比「全部自建」更精确）

- **抄**：`competitor-monitor-claw` 的架构（已留档 `memory/skills-ref/competitor-monitor-claw/`）

## 10-26 数据轮的三条修正（对我此前建议的更新）

> 依据：`memory/hotel-industry/reports/2026-10-26-酒店文旅行业快讯.md`（每条带置信度四档+口径+边界）

### 修正 1｜存量翻新的**退出估值假设要保守**（此前我给的是「雅高 Essendi 卖资产骨架」）
- JLL：亚太酒店投资 1–9 月 **120 亿美元 / +50%**，2019 年以来最强；但**日本占 39%，中国大陆仅 15%**
  → 中国存量资产的**买方流动性不宽裕**（🟡🟡）
- **含义**：雅高那套「卖资产、留品牌、锁长约」是**可抄的机制**，但**中国市场的变现假设不能照搬**；
  我此前的表述偏向「退出路径原型」，现在要补一句：**先看中国买方的钱从哪来，再谈退出定价。**

### 修正 2｜改造的**优先级应按「提价型 vs 重投入型」分层**，不是「改造即好」
- STR 周度（10 月第 2 周，长江社服第 42 周口径）：内地 RevPAR 同比 **+0.4% 转正**，
  **OCC -0.9% / ADR +1.3% = 量减价增**；滚动 28 天跌幅收窄 0.6pct
  → 分层次：**奢华 +2.0%／中高端 -2.9%／经济型 +2.0%**（🟡🟡）
- **含义**：
  - **提价型存量改造**（低投入、靠硬件老化提价 + 定位）→ **优先级上调**（ADR 弹性能兑现）
  - **高投入中高端改造** → 中高端 -2.9%，**必须重算 ROI**，不能按「ADR 全面回暖」定价
- **制度前提**：9-15 两部门 OTA 行政指导（六平台承诺不做「独家合作」「全网最低价」）
  → **单体跨平台定价权回升**，这是 ADR 弹性能兑现的前提（⚠️ 行政指导无强制力）

### 修正 3｜「中国区承压是全球共识」要**加口径注**，不能笼统用
- STR 周度 RevPAR **+0.4% 转正**（周度口径）与 10-25 记录的「5 家国际集团中国区同步承压」
  （集团季度口径）**不冲突** —— **周度 STR 口径 ≠ 集团季度口径，混用会误判**
- IHG Q3 官方原文（10-22，🟢🟢 首采）：全球 RevPAR +5.3% / **大中华 -3.3%**；
  管线 353k 间 = 系统规模 33%
- **修正后的表述**：
  「中国区**集团季度口径**承压（IHG/温德姆/希尔顿/雅高 4–5 源同向），
  但**周度 STR 口径已转正（量减价增）** → **不是单向崩塌，是量价分化 + 档次分化**」
  → 对模型的含义：**不能用单一方向假设做 ADR 预测**（这直接影响我给的自建方案里的定价模型输入侧）

### 附带：一条**新增的制度性理由**，强化了「竞品房价监控」的价值
9-15 OTA 行政指导后**平台不再强制「全网最低价」** → 单体的价格竞争力**只能自己盯**跨平台价
→ 「酒店竞品房价监控」从「想做的事」变成「**制度上必须自己做的事**」，
这是本轮为该自建方案新增的最强论据。

## STR 缺口的替代路径实测（2026-10-26）—— 结论：**STR key 仍是最优，但**它**不是**自建的阻塞项

我实测了「不用 STR_API_KEY、改为自动抓酒店集团 IR 月度经营数据公告」这条替代路径：

| 目标 | 实测结果 |
|---|---|
| 锦江 `http://www.jinjianghotels.com.cn/investor` | **HTTP 404**（路径不存在） |
| 首旅 `http://www.bthhotels.com/investor` | **HTTP 404** |
| 华住 `https://ir.huzhu.com` | **SSL EOF**（TLS 握手被挡，直连不通） |
| 亚朵 `https://ir.atour.com` | **SSL EOF** |
| 6 个「定期报告 / 公告」深路径 | 全 404 |

→ **IR 路线在本机的 urllib+TLS 栈下不可用**（这正是本地 MOTI 之所以要用
chrome-devtools + AI 视觉解析的原因 —— 同一类站点、同一道坎）。
→ 顺带发现并修掉 collector 的一个**休眠 bug**：`collect_stock_data` 里 4 个 IR URL
（2 个 404 + 2 个 SSL 失败）此前从未被 config 启用，所以一直藏着；已改为可达入口 + 显式标注。

**三条路的取舍（给你的决策 #4 补依据）**
| 路径 | 自动化 | 可回溯 | 成本 |
|---|---|---|---|
| **A. STR_API_KEY**（推荐） | ✅ | ✅ | 需你提供 key（付费订阅） |
| B. IR 月度经营数据（用浏览器态） | ⚠️ 可做 | ⚠️ 需自建爬虫 | 工程量≈MOTI 的浏览器改造 |
| C. web_search 补 STR 周度 | ❌ 手工 | ❌ | 现状（10-26 轮就是这么补的） |

**但请注意一个关键区分（这解除了自建方案的阻塞）**：
- **STR = 全市场周度趋势**（OCC/ADR/RevPAR 的市场基准）
- **自建方案要的是「竞对挂牌价」** → **这一层 MOTI 已覆盖**（携程/美团/去哪儿/飞猪 + AI 视觉 + OCC 加权）
→ **所以「竞品房价监控」自建**不需要** 等 STR key**；STR key 只影响
「市场基准趋势」这一辅助输入。**决策 #3（启动阶段 0）可以现在就做，不用等 key。**
